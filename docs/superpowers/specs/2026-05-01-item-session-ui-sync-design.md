# 事项绑定会话 UI 同步修复设计

## 背景

当前“事项面板 -> 新建会话”并不会立刻创建服务端会话，只是将页面切到空白会话态。用户发送首条消息后，前端才向 opencode server 创建真实会话，并在后续流程中将该会话绑定到当前事项。

现象是：

1. 数据层面上，该新会话已经绑定到当前事项。
2. 但 UI 没有及时反映绑定结果。
3. 项目管理面板中的会话列表仍会把该会话当作“未绑定事项的会话”来处理。
4. 事项面板中的“事项会话列表”没有显示这个新会话。

## 问题定义

预期行为：

1. 只有在用户发送首条消息、真实会话创建成功后，才需要更新 UI。
2. 项目管理面板的会话列表只显示“未绑定事项”的会话。
3. 新会话一旦绑定到当前事项，就不应进入项目管理面板的未绑定会话列表。
4. 同一时刻，该会话应立即出现在当前事项的事项会话列表中。
5. 整个过程不依赖手动刷新，也不依赖 `loadProject` 全量刷新。

## 根因

当前流程中，首条消息发送后会完成两件事：

1. 创建真实会话。
2. 将会话 summary 的 `itemId` 写入服务端。

但在服务端写入成功后，前端没有把更新后的 summary 同步回本地 `itemWorkspaceStore.projectStates[projectPath].summaries`。

因此两个 UI 区域都在读取过期的本地 summary：

- 项目管理面板仍把该会话视为未绑定事项。
- 事项面板无法按 `summary.itemId === 当前事项.id` 找到该会话。

## 设计目标

以最小改动修复本次同步问题：

1. 保持现有“点击新建会话不立即创建服务端会话”的交互模型。
2. 保持现有“首条消息后补绑定事项”的数据流。
3. 仅补充本地 store 的 summary 同步。
4. 不引入全量刷新。
5. 不做额外重构。

## 方案对比

### 方案 A：补本地 summary 同步（采用）

在首条消息创建会话成功、并完成事项绑定后，拿到最新 summary，立即写回本地 `itemWorkspaceStore`。

优点：

- 改动最小。
- UI 更新快。
- 符合当前由本地 store 驱动两个面板渲染的实现方式。

缺点：

- 需要确保写回逻辑与现有 summary 结构一致。

### 方案 B：绑定成功后全量 `loadProject`

优点：

- 实现直接。
- 不容易漏字段。

缺点：

- 刷新成本更高。
- UI 反馈更慢。
- 会引入不必要的数据重载。

### 方案 C：重构创建/绑定流程

优点：

- 长期结构更统一。

缺点：

- 超出本次 bugfix 范围。
- 改动面过大。

## 采用方案

采用方案 A。

在当前“首条消息后完成会话绑定”的路径上，补一层本地 summary 回写，使两个面板基于同一份最新 summary 立刻收敛到正确状态。

## 目标数据流

1. 用户在事项面板点击“新建会话”。
2. 前端进入空白会话态，并记录 pending item binding。
3. 用户发送首条消息。
4. 前端创建真实会话。
5. 前端将该会话 summary 绑定到当前事项，服务端返回带 `itemId` 的最新 summary。
6. 前端立即将该 summary 写回本地 `itemWorkspaceStore.projectStates[projectPath].summaries`。
7. 项目管理面板再次取数时，因为该 summary 已有 `itemId`，不会进入“未绑定事项会话”列表。
8. 事项面板再次取数时，因为该 summary 的 `itemId` 等于当前事项 id，会立即显示在事项会话列表中。

## 改动范围

主要改动点：

- `src/hooks/useChatSession.ts`
  - 在首条消息后的事项绑定流程里，补本地 summary 回写。

参考对齐位置：

- `src/store/itemWorkspaceStore.ts`
  - 复用或对齐现有 summary 写回模式，避免引入第二套不一致逻辑。

受影响展示：

- 项目管理面板会话列表
- 事项面板事项会话列表

## 实现约束

1. 不改变“新建会话”按钮的现有语义。
2. 不在点击按钮时提前创建服务端会话。
3. 不新增额外请求链路。
4. 不使用全量 `loadProject` 作为修复手段。

## 错误处理

如果服务端绑定 summary 失败，则维持现有失败行为，不额外伪造本地绑定状态。

如果服务端绑定成功但本地回写失败，则应让错误暴露在开发阶段，而不是静默吞掉；因为这会再次导致“服务端正确、前端错误”的状态分裂。

## 验收标准

### 场景 1：从事项面板发起新会话

1. 在事项面板点击“新建会话”。
2. 页面进入空白会话态。
3. 发送首条消息后，会话创建成功。
4. 该会话不会出现在项目管理面板的未绑定会话列表中。
5. 该会话会立即出现在当前事项的事项会话列表中。

### 场景 2：刷新前即时一致性

1. 首条消息发送成功后，无需手动刷新页面。
2. 两个面板都立即反映新的事项绑定状态。

### 非目标

1. 不处理空白会话态的额外占位展示。
2. 不修改会话创建时机。
3. 不重构事项与会话绑定体系。
