# 事项绑定会话过滤修复设计

## 背景

当前事项面板右上角的“绑定会话”按钮会打开本项目会话列表，供用户把已有会话绑定到当前事项。

现有问题是：

1. 列表中混入了已经绑定到当前事项的会话。
2. 这会让“可绑定列表”与“已绑定列表”语义重叠。
3. 用户会误以为同一个会话还能重复绑定。

根据本次确认的产品边界：

1. 绑定弹窗里只应显示“当前未绑定到任何事项”的会话。
2. 如果一个会话以前绑定过、后来解绑了，它仍应重新出现在列表里，允许再次绑定。

## 问题定义

当前事项面板的绑定弹窗会同时依赖两类数据：

1. `getSessionsForDirectory(...)` 返回的原生会话列表。
2. `itemWorkspaceStore` 中的事项会话 summary。

预期行为应为：

1. 当前已经绑定到该事项的会话，不出现在“可绑定列表”中。
2. 当前绑定到其他事项的会话，也不出现在“可绑定列表”中。
3. 当前未绑定的会话应正常显示。
4. 曾经绑定但现在已解绑的会话，应重新进入“可绑定列表”。

## 根因

当前过滤逻辑位于 `src/features/items/ItemDetailPanel.tsx`：

1. 它先根据 `linkedSessions` 计算当前事项已绑定的 `boundIds`。
2. 再根据 `unboundSessions` 建立 `summariesByExternalId`。
3. 最终用以下规则筛选：

   - 不在 `boundIds` 中的会话显示。
   - 或者，只要该会话在 `unboundSessions` 中有 summary，也显示。

这个实现的问题在于：

1. “可绑定列表”的判定散落在组件内部。
2. 过滤条件依赖“当前事项已绑定 + 当前项目未绑定 summary”的组合推断，语义不够直接。
3. 当某个会话同时存在原生 session 与 summary 记录时，列表容易出现与“仅显示未绑定会话”目标不一致的结果。

## 设计目标

以最小改动修复本次问题：

1. 绑定弹窗只显示当前未绑定的会话。
2. 已解绑会话仍允许再次绑定。
3. 保持现有绑定/解绑 API 与数据模型不变。
4. 仅收敛绑定弹窗的过滤语义，不扩展到其他列表重构。

## 方案对比

### 方案 A：在 `ItemDetailPanel` 修正过滤逻辑（采用）

做法：

1. 保持 `getSessionsForDirectory(...)` 取原生会话。
2. 保持 `linkedSessions` / `unboundSessions` 作为现有输入。
3. 在组件内把过滤规则明确收敛为：
   - 若会话当前已绑定，则不显示。
   - 若会话当前未绑定，则显示。
   - 若该会话有未绑定 summary，则优先复用该 summary 执行重新绑定。

优点：

1. 改动最小。
2. 风险最低。
3. 不需要改 store 或后端接口。

缺点：

1. 过滤语义仍留在组件层。

### 方案 B：把“可绑定会话”收口到 store selector

做法：

1. 在 `itemWorkspaceStore` 中新增或改造 selector。
2. 由 store 统一给出“当前项目可绑定会话”的集合。
3. `ItemDetailPanel` 只负责展示。

优点：

1. 语义更集中。
2. 后续其他组件复用更方便。

缺点：

1. 改动面更大。
2. 需要把原生 session 与 summary 的拼装逻辑进一步下沉。
3. 超出本次 bugfix 必要范围。

### 方案 C：后端直接返回“可绑定会话”

做法：

1. 服务端按事项绑定状态过滤会话。
2. 前端直接渲染后端返回的结果。

优点：

1. 一致性最好。
2. 前端判断最少。

缺点：

1. 成本最高。
2. 需要新增服务端约束与接口语义。
3. 不符合本次最小修复目标。

## 采用方案

采用方案 A。

核心原则：

1. 绑定弹窗的职责只是展示“当前可绑定的会话”。
2. “可绑定”的定义是：当前没有绑定到任何事项。
3. “历史上绑定过但现已解绑”不属于排除条件。

## 目标数据流

1. 用户打开事项面板的“绑定会话”弹窗。
2. 前端调用 `getSessionsForDirectory(...)` 获取当前项目下的原生会话列表。
3. 前端同时读取：
   - `linkedSessions`：当前事项已绑定 summary
   - `unboundSessions`：当前项目未绑定 summary
4. 前端基于“当前是否仍绑定”过滤原生会话：
   - 当前已绑定的原生会话排除
   - 当前未绑定的原生会话保留
5. 如果某个原生会话存在未绑定 summary，则点击时直接复用该 summary 绑定到当前事项。
6. 如果某个原生会话没有对应 summary，则沿用现有 `onBindProjectSession(...)` 路径创建/绑定。

## 改动范围

主要改动点：

- `src/features/items/ItemDetailPanel.tsx`
  - 收紧绑定弹窗的会话过滤逻辑。
  - 明确“只排除当前已绑定会话，不排除已解绑历史会话”。

参考但原则上不改：

- `src/store/itemWorkspaceStore.ts`
  - 继续复用 `getProjectUnboundSummaries(...)` 与 `getLinkedSummaries(...)`。

- `src/App.tsx`
  - 继续透传 `linkedSummaries` 与 `unboundSummaries` 给事项面板。

## 实现约束

1. 不修改绑定/解绑接口。
2. 不新增后端请求。
3. 不调整事项面板以外的会话列表展示。
4. 不把本次 bugfix 扩展为 store / server 结构性重构。

## 错误处理

1. 如果会话列表请求失败，继续保持当前空列表兜底行为。
2. 如果会话有未绑定 summary，则优先走已有 summary 绑定，避免重复创建 summary。
3. 本次不新增额外错误提示，只保证过滤语义正确。

## 验收标准

### 场景 1：当前已绑定会话

1. 某会话已绑定到当前事项。
2. 打开“绑定会话”弹窗。
3. 该会话不出现在列表中。

### 场景 2：当前未绑定的新会话

1. 某会话当前没有绑定任何事项。
2. 打开“绑定会话”弹窗。
3. 该会话出现在列表中，可正常绑定。

### 场景 3：曾绑定后解绑的会话

1. 某会话曾绑定过事项，后来已解绑。
2. 打开“绑定会话”弹窗。
3. 该会话重新出现在列表中。
4. 点击后可重新绑定到当前事项。

## 非目标

1. 不处理事项列表、项目列表等其他区域的展示规则。
2. 不重构 `itemWorkspaceStore` 的 selector 结构。
3. 不新增服务端“可绑定会话”接口。
