# 邮箱密码认证设计

## 1. 背景

当前 OpenCodeUI 只支持 GitHub OAuth 登录。

由于测试环境与生产环境域名不同，GitHub 登录在部分场景下不可用，因此需要补充邮箱密码注册与登录能力。同时，生产环境仍需继续保留 GitHub 登录。

本次设计目标是在不重写现有 session 体系的前提下，让系统同时支持：

1. GitHub OAuth 登录
2. 邮箱注册
3. 邮箱密码登录
4. GitHub 账号与邮箱账号按邮箱自动合并

## 2. 范围

### 2.1 本期包含

1. 邮箱注册
2. 邮箱密码登录
3. GitHub 登录继续保留
4. GitHub 回调时基于邮箱自动合并账号
5. 登录弹窗支持 GitHub 与邮箱密码双入口

### 2.2 本期不包含

1. 忘记密码
2. 重置密码
3. 邮箱验证
4. GitHub 登录后立即设置密码流程
5. 账号绑定管理页
6. 修改密码入口

## 3. 现状

当前认证实现特点：

1. 仅支持 GitHub OAuth 登录
2. session 通过服务端 cookie + SQLite 持久化
3. `users` 表当前仅承载 GitHub 相关身份字段
4. 前端登录弹窗当前仅引导用户跳 GitHub

现有会话体系可继续复用，本次仅扩展用户识别与登录入口。

## 4. 设计目标

1. 让用户可直接通过邮箱注册并登录
2. 保持 GitHub 登录能力不受影响
3. 尽量复用现有 session cookie 与 `/auth/me` 流程
4. 避免同一邮箱产生重复账号
5. 保持最小实现范围，不引入找回密码等额外流程

## 5. 用户模型

### 5.1 用户表能力扩展

`users` 表扩展后支持三类账号状态：

1. 纯邮箱账号
   - `email`
   - `password_hash`
2. 纯 GitHub 账号
   - `github_id`
   - 可选 `email`
   - 无 `password_hash`
3. 混合账号
   - `github_id`
   - `email`
   - `password_hash`

### 5.2 字段约束

建议新增或确认以下约束：

1. `email` 可为空，但非空时必须唯一
2. `github_id` 可为空，但非空时必须唯一
3. `password_hash` 可为空
4. `email` 入库前统一做：
   - 去首尾空格
   - 转小写

这样既能兼容旧 GitHub 用户，也能支持未来一个账号绑定多种登录方式。

## 6. 登录方式规则

### 6.1 邮箱注册

用户提交 `email + password` 后：

1. 对邮箱做规范化处理
2. 校验邮箱格式
3. 校验密码规则：
   - 至少 8 位
   - 必须包含字母
   - 必须包含数字
4. 若邮箱已存在，则返回“邮箱已注册”
5. 若邮箱不存在，则创建新用户并写入 `password_hash`
6. 注册成功后立即创建 session，用户直接进入已登录状态

### 6.2 邮箱密码登录

邮箱密码登录必须同时满足：

1. 用户存在
2. 用户存在 `password_hash`
3. 密码校验通过

以下场景统一返回 `邮箱或密码错误`：

1. 邮箱不存在
2. 密码错误
3. 用户是仅 GitHub 账号，尚未设置本地密码

### 6.3 GitHub 登录

GitHub OAuth 登录继续沿用现有流程：

1. 前端获取 GitHub authorize URL
2. 浏览器跳转 GitHub
3. GitHub 回调服务端
4. 服务端建立 session cookie
5. 前端刷新 `/auth/me` 恢复登录态

本次只调整 GitHub 回调时的账号查找与合并逻辑。

## 7. 账号自动合并规则

### 7.1 合并目标

当同一邮箱既用于邮箱注册，也出现在 GitHub 返回资料中时，应自动合并为同一个账号，避免重复用户。

### 7.2 GitHub 回调处理顺序

GitHub 登录成功后按以下顺序处理：

1. 先按 `github_id` 查找用户
   - 若找到：直接登录，并同步 GitHub 资料
2. 若未找到，且 GitHub 返回邮箱
   - 对邮箱做规范化处理
   - 按邮箱查找用户
   - 若找到：将 `github_id` 绑定到该用户
3. 若仍未找到用户
   - 创建新用户
   - 写入 `github_id`
   - 若 GitHub 返回邮箱则一并写入 `email`

### 7.3 GitHub 返回邮箱后的邮箱登录能力

若用户先通过 GitHub 登录，且 GitHub 返回了邮箱：

1. 系统会记录该邮箱
2. 下次 GitHub 登录仍可直接使用该 GitHub 账号
3. 但若该账号没有 `password_hash`，仍不能使用邮箱密码登录

也就是说：

- GitHub 返回邮箱，只代表账号可识别该邮箱
- 只有该账号拥有 `password_hash` 时，邮箱密码登录才成立

### 7.4 异常冲突保护

理论上由于唯一约束，不应出现脏数据冲突。但若发生以下异常：

1. `github_id` 命中一个用户
2. `email` 命中另一个不同用户

则应拒绝自动合并并返回认证失败，避免账号串绑。

## 8. 接口设计

### 8.1 现有接口保留

1. `GET /auth/me`
2. `GET /auth/github/login`
3. `GET /auth/github/callback`
4. `POST /auth/logout`

### 8.2 新增接口

1. `POST /auth/register`
2. `POST /auth/login`

### 8.3 `POST /auth/register`

请求体：

```json
{
  "email": "user@example.com",
  "password": "abc12345"
}
```

处理逻辑：

1. 规范化邮箱
2. 校验邮箱格式
3. 校验密码规则
4. 检查邮箱是否已存在
5. 创建用户并保存 `password_hash`
6. 创建 session
7. 返回当前用户信息

失败语义：

1. 邮箱格式错误
2. 密码不符合规则
3. 邮箱已注册

### 8.4 `POST /auth/login`

请求体：

```json
{
  "email": "user@example.com",
  "password": "abc12345"
}
```

处理逻辑：

1. 规范化邮箱
2. 按邮箱查找用户
3. 校验是否存在 `password_hash`
4. 校验密码
5. 创建 session
6. 返回当前用户信息

失败语义统一为：

`邮箱或密码错误`

## 9. 前端交互设计

### 9.1 登录弹窗结构

当前登录弹窗从“仅 GitHub 按钮”升级为双入口弹窗：

1. 邮箱密码登录表单
2. 邮箱注册表单
3. GitHub 登录按钮

### 9.2 登录态界面

默认进入登录态，展示：

1. 邮箱输入框
2. 密码输入框
3. 登录按钮
4. GitHub 登录按钮
5. “没有账号？去注册”切换入口

### 9.3 注册态界面

切换后展示：

1. 邮箱输入框
2. 密码输入框
3. 注册按钮
4. “已有账号？去登录”切换入口
5. GitHub 登录按钮

### 9.4 交互行为

1. 注册成功后直接进入已登录状态
2. 登录成功后关闭弹窗并刷新认证状态
3. GitHub 登录继续使用跳转 OAuth 流程
4. 现有匿名继续使用能力默认保持不变

## 10. 安全设计

### 10.1 密码存储

密码必须只存哈希，不存明文。

实现上应使用成熟的密码哈希算法，如：

1. `bcrypt`
2. `argon2`

具体选型可在实现计划中结合当前项目依赖再定，但必须满足：

1. 有随机盐
2. 可安全比对
3. 不自行实现哈希逻辑

### 10.2 错误暴露策略

为降低撞库与枚举风险：

1. 登录失败不区分“邮箱不存在”还是“密码错误”
2. 注册失败可明确提示“邮箱已注册”

### 10.3 输入规范化

邮箱字段统一做：

1. `trim`
2. `lowercase`

避免同一邮箱大小写差异导致重复账号。

## 11. 数据迁移与兼容性

### 11.1 迁移策略

现有 `users` 表需新增：

1. `email`
2. `password_hash`

若当前 SQLite 初始化逻辑是建表式迁移，则需要补充兼容旧库的增量迁移逻辑，例如：

1. 缺列时执行 `ALTER TABLE`
2. 为新列补建唯一索引

### 11.2 对旧用户的影响

旧 GitHub 用户：

1. 不受影响
2. 可继续 GitHub 登录
3. `email` 与 `password_hash` 可为空
4. 若未来补设密码，才具备邮箱密码登录能力

因此本次变更是向后兼容的能力扩展。

前端统一展示：

1. 邮箱或密码错误

## 15. 实现边界总结

本期最终边界如下：

1. 全环境同时支持 GitHub 与邮箱密码登录，不做环境分流
2. 支持任意邮箱注册
3. 不要求邮箱验证
4. 密码规则为至少 8 位且包含字母和数字
5. GitHub 返回邮箱时按邮箱自动合并账号
6. GitHub 账号若没有本地密码，暂时不能直接用邮箱密码登录
7. 不扩展找回密码、重置密码、修改密码等后续能力

## 16. 结论

该方案通过最小范围扩展现有认证体系，实现了：

1. GitHub 与邮箱密码双登录入口并存
2. 基于邮箱的自动账号合并
3. 对旧 GitHub 用户与现有 session 体系的兼容

它满足当前“测试环境无法依赖 GitHub 登录”的问题，同时不牺牲生产环境的 GitHub 登录能力，也为后续补设密码、密码管理等能力预留了清晰的演进空间。
