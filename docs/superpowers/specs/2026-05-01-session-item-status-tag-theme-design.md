# 会话与事项状态 Tag 主题化设计

## 背景

项目面板中的会话列表、事项列表，以及事项详情中的关联会话列表，都会在标题前显示一个类型 tag，例如“会话”“需求”“审查”。

当前这些 tag 的颜色由状态驱动：

- `not_started`
- `in_progress`
- `completed`
- `abandoned`

现有实现直接在组件中写死了状态对应的 Tailwind 色值，例如浅透明背景配亮色文字。这个方案在深色主题下还能工作，但在浅色主题下对比度过低：

1. 文字颜色偏浅。
2. 背景色承托不足。
3. 白色背景下识别成本高，需要刻意盯着看才能分辨 tag 文本。

## 问题定义

本次要解决的问题不是“是否继续按状态着色”，而是“在保留状态语义的前提下，让明暗主题下的 tag 都可读”。

确认后的产品边界：

1. tag 继续按状态变色。
2. 不把“会话 / 需求 / 审查”本身拆成独立颜色体系。
3. 需要同时覆盖：
   - 项目面板中的会话列表
   - 项目面板中的事项列表
   - 事项详情中的关联会话列表
   - 其他复用同一 tag 渲染逻辑的区域
4. 本次不重构业务状态逻辑，只解决视觉 token 组织和可读性问题。

## 设计目标

1. 保留现有状态语义，不改变用户对颜色含义的认知。
2. 去掉组件内部硬编码状态色值。
3. 引入按主题切换的状态 tag token。
4. 提升浅色主题下的文字与背景对比度。
5. 保持深色主题下现有轻量风格，但避免颜色发灰、发飘。
6. 让后续调色只需改 token，而不需要改组件逻辑。

## 方案对比

### 方案 A：继续在组件中直接写色值

做法：

1. 直接修改 `SessionListItem` 中的状态 class。
2. 给浅色主题手动换一组更深的 Tailwind 类。

优点：

1. 改动最少。
2. 实现最快。

缺点：

1. 颜色逻辑继续散落在组件里。
2. 明暗主题分支会越来越难维护。
3. 后续再调色仍要进组件改实现。

### 方案 B：抽象状态 tag 主题 token（采用）

做法：

1. 在全局主题层定义状态 tag 的背景色与文字色 token。
2. 组件只负责把状态映射到 token，不再知道具体颜色值。
3. light / dark theme 分别提供不同 token 值。

优点：

1. 颜色语义集中，维护成本低。
2. 组件逻辑更简单。
3. 后续继续调色或扩展状态时更稳定。
4. 可以统一覆盖多个列表，避免同状态在不同地方观感不一致。

缺点：

1. 比直接改 class 多一层主题映射。
2. 改动面略大于一次性硬编码修补。

### 方案 C：统一改成中性 tag，不再按状态着色

优点：

1. 对比度问题最容易控制。
2. 视觉更统一。

缺点：

1. 丢失当前状态语义。
2. 不符合本次已确认边界。

## 采用方案

采用方案 B：抽象状态 tag 主题 token。

核心原则：

1. 状态语义继续保留。
2. 视觉颜色由主题 token 提供。
3. 组件只保留“状态 -> token”的映射职责。

## Token 结构

新增一组按状态划分的语义 token，至少包含：

- `--status-tag-not-started-bg`
- `--status-tag-not-started-text`
- `--status-tag-in-progress-bg`
- `--status-tag-in-progress-text`
- `--status-tag-completed-bg`
- `--status-tag-completed-text`
- `--status-tag-abandoned-bg`
- `--status-tag-abandoned-text`

这些 token 在 light theme 与 dark theme 下分别给出不同值。

本次只要求覆盖 tag 的背景色与文字色，不额外扩展边框、hover、selected token。

## 视觉规则

### 浅色主题

目标：白底下能直接读清 tag 文本。

规则：

1. 文字色明显加深，不再使用高亮但发浅的 pastel 字色。
2. 背景色保留轻量感，但需要足够承托文字。
3. 四种状态继续保持稳定区分：
   - `not_started`：偏紫
   - `in_progress`：偏蓝
   - `completed`：偏绿
   - `abandoned`：偏灰

### 深色主题

目标：保留当前轻量感，但避免颜色只剩一层很淡的雾。

规则：

1. 保留亮色文字 + 低透明色底的整体方向。
2. 略提高底色承托感。
3. 灰色状态单独控制，避免在暗底上糊掉。

### 统一约束

1. 同一状态在所有复用区域颜色一致。
2. 本次只修改 tag 自身，不修改标题正文、hover、选中态。
3. “会话 / 需求 / 审查”仍然共用同一套按状态变化的颜色规则。

## 代码落点

### 1. 全局主题定义

在全局主题样式文件中定义 token，优先放在 `src/index.css` 的主题变量区。

### 2. 状态映射逻辑

当前 `src/features/chat/sidebar/SessionListItem.tsx` 中有 `getStatusTagClass(status)`，直接返回写死的 Tailwind 类。

本次调整为：

1. 继续保留状态分支。
2. 但返回改为基于 token 的 class / style 映射。
3. 组件不再持有具体颜色常量。

### 3. 复用覆盖

以下区域通过复用 `SessionListItem` 自动吃到新样式：

1. 项目面板里的会话列表。
2. 项目面板里的事项列表。
3. 事项详情中的关联会话列表。

如果有其他地方复用同一 tag 渲染路径，也一并统一。

## 目标数据流

1. 渲染列表项时，组件拿到 `tagStatus`。
2. 组件根据状态选择对应的语义 token。
3. 当前主题提供 token 的具体颜色值。
4. tag 最终根据主题自动呈现不同的背景色和文字色。
5. 切换 light / dark theme 后，无需改组件逻辑，只切换 token 值。

## 改动范围

主要改动点：

- `src/index.css`
  - 新增状态 tag 的 light / dark theme token。

- `src/features/chat/sidebar/SessionListItem.tsx`
  - 把状态 tag 的硬编码色值改成 token 映射。

联动影响：

- 所有复用 `SessionListItem` 渲染状态 tag 的区域。

## 实现约束

1. 不改业务状态枚举。
2. 不新增后端字段。
3. 不把本次工作扩展成完整 design system 重构。
4. 不修改 tag 之外的列表 hover、selected、title 颜色。

## 错误处理

本次为纯前端视觉调整，没有新增异步链路或错误分支。

需要重点防止的是样式回归：

1. token 未覆盖某个主题时，不能让 tag 退回不可读状态。
2. 状态默认分支需要有可接受的兜底样式。

## 验收标准

### 场景 1：浅色主题

1. 查看项目面板中的会话 tag。
2. 查看项目面板中的事项 tag。
3. 查看事项详情中的关联会话 tag。
4. 文本在白底下应当直接可读，无需刻意辨认。

### 场景 2：深色主题

1. 同样检查上述三类区域。
2. 不同状态仍然容易区分。
3. tag 不应发灰、发虚。

### 场景 3：状态覆盖

以下状态都需要正常渲染：

1. `not_started`
2. `in_progress`
3. `completed`
4. `abandoned`

### 场景 4：非目标回归

1. hover 态不应被意外改坏。
2. selected 态不应被意外改坏。
3. 列表标题正文颜色不应受影响。
4. 状态语义保持不变。

## 非目标

1. 不重构成完整的全局 tag 设计系统。
2. 不统一其他无关 badge / tag。
3. 不调整状态业务逻辑。
4. 不修改会话标题、事项标题的排版与层级。
